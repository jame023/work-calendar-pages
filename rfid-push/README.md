## Behavior

Each Android or iPhone/iPad installs the PWA, opens it from its Home Screen icon, then opts in and grants notification permission. Every enrolled phone can receive named check-in/out events for all employees, with the original Bangkok scan date/time. On iPhone/iPad, use iOS/iPadOS 16.4+. Notifications depend on connectivity, device notification settings, and the push provider. No exact delivery time or guaranteed physical phone delivery is claimed.

The worker polls the existing anonymous `api=rfid-public` endpoint every 30 seconds. The current and previous scan days are read to cover midnight and recent delayed retries. No source reads occur if there are no enabled devices. A normal notification has polling plus provider/queue latency. A large fan-out can take multiple polling rounds. Scan events older than the previous day, upstream API truncation, and provider failures cannot be repaired by changing this independent notifier; source ingestion reports an error rather than accepting an incomplete page. Only named `เข้างาน` / `เลิกงาน` with valid chain evidence are forwarded. Duplicate scans and unknown cards do not establish attendance notifications.

Google Sheets, Apps Script source/deployment, attendance calculations, Phase 1B transactions, and hardware firmware/protocol remain unchanged. The Gateway's literal `OK RFID` response stays in the existing backend.

## Persistence and retry

`schema.sql` creates only the new `rfid_push_*` tables and invoker RPCs in this dedicated project. RLS and explicit grants prevent anonymous/authenticated Data API access to device endpoints, capabilities, private VAPID settings, events, and deliveries. An anonymous JWT is public client configuration; service-role credentials are supplied only by the Edge runtime.

Event IDs are copied from the verified audit API. SEQ is never a deduplication key. Event ingestion and per-device delivery insertion are one transaction. Event IDs have unique storage; deliveries have a unique `(event_id, device_id)` key. A conflicting fingerprint fails the transaction. Worker and delivery leases recover after crashes. Transient network/429/5xx responses remain retryable; 404/410 deactivate expired endpoints. Successful deliveries are not resent by a normal retry. Uncertain provider acceptance followed by database failure can resend the same payload. Service-worker notification tags replace a currently visible retry with `renotify: false`; a dismissed notification can reappear. Exactly-once physical phone display cannot be guaranteed. Every push displays a visible notification to satisfy Safari's Web Push requirements.

Subscriptions apply to events received after opt-in, with the source API's one-second timestamp resolution. Earlier events are not broadcast when enabling. Disabling, reenabling, or replacing subscription keys invalidates that endpoint's old pending/sending deliveries and clears their lease tokens while preserving sent deduplication records. Obsolete completions cannot disable a renewed enrollment. Ingestion locks each device before evaluating its current eligibility and creating the delivery. Device-before-delivery lock ordering is shared by ingestion, enrollment, authorization, and completion. Each provider attempt is individually reauthorized by `rfid_push_begin_send` using current enrollment, delivery ownership, and worker/delivery leases; a claimed JavaScript batch is not permission to send later canceled rows. Already authorized/in-flight provider attempts cannot be recalled across the network boundary. A 24-hour delivery window limits backlog. An independent hourly SQL job removes events older than three days, devices disabled for seven days, and this feature's cron history older than one day, even without enabled devices or healthy source ingestion. Retention can extend by the cleanup cadence; it never touches attendance or another job's logs.

If a source request or validation fails, no partial new batch is ingested. Already verified persisted deliveries can still be drained, and the worker records the source error with `ok: false` for that round. Database/identity errors fail the round and retain recoverable leases. The PWA confirms the active worker has a push handler through a message-port handshake before enabling; an old active worker asks the user to reopen/refresh, with local opt-out still available.

## Free usage bounds

30-second polling is 86,400 invocations in 30 days (89,280 in 31 days), plus device configuration/enrollment/test calls. Current Free quotas are 500,000 Edge invocations/month, 500 MB database/project, and 5 GB egress/month. Enrollment is capped at 200 enabled phones; delivery claims and test notifications share one atomic budget of no more than 100,000 reserved attempts/calendar month, including failed provider attempts. Budget exhaustion leaves the attendance queue pending until its delivery lifetime or a later quota reset and rejects test sends; it does not buy resources or upgrade the plan. A test notification is also limited to one per device per minute. Test admission locks the worker before the device, matching ingestion's lock order. These bounds reduce normal usage but cannot control other applications or third-party traffic in the same Organization.

## Setup and release boundary

1. Review the complete source, schema, cron, config, tests, package lock, and Deno configuration against the exact GitHub and Supabase targets. Independent reviewer and literal `codex review` must both PASS before any source push, schema application, or function deployment. Re-review changed files or destinations.
2. Apply `schema.sql` once to the new, empty RFID push project. Never run it in the existing application project.
3. Generate a stable P-256 VAPID pair and a 32-byte random cron capability with a cryptographically secure generator. Insert one private settings JSON row into `rfid_push_settings`; keep the private key/capability out of source control and frontend. Settings fields: `origin`, `sourceUrl`, `subject`, `vapidPublicKey`, `vapidPrivateKey`, `cronToken`, `startedAt` (UTC ISO instant), `functionUrl`, and `anonKey`. Use the established central Apps Script URL copied from the PWA. Do not rotate VAPID keys during routine deployment.
4. Deploy `functions/rfid-push/index.ts`, relative files, and `deno.json` as Edge Function `rfid-push`, with JWT verification enabled. The built-in `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` stay server-only. The direct npm library is pinned at `web-push@3.6.7`, and the Node verification dependencies are pinned by `package-lock.json`. Supabase's remote npm bundling must also be verified before publishing the PWA.
5. Verify public config, JWT enforcement, enrollment ownership, and safe source ingestion. Before cron or user enrollment, run the two-session SQL protocol returned by `buildConcurrencyProbe()` in `test/concurrency-probe.js` through the connected database admin tools. Run `setup`, start `hold` asynchronously, wait until `observe.holding` is true, then start `ingest` concurrently. While both calls run, require `observeBlocked.overlapping_lock: true`, proving the tagged ingest session is blocked by the tagged enrollment session through `pg_blocking_pids`; a serialized/delayed request is not a passing concurrency test. Await both sessions. `verify` must report `event_stored: true, old_deliveries: 0`; `fresh.authorized` must be true and `cancel.still_authorized` false. Always run `cleanup`, including on failure. The protocol refuses an active device/worker, uses a synthetic fixture only, and makes no provider request. Then apply `enable-cron.sql` and verify the 30-second job and log cleanup are active. Its SQL reads the private cron capability from the restricted settings row; no secret is embedded in public SQL.
6. Publish the reviewed PWA files at the existing GitHub Pages URL. `push-config.json` contains only the public function URL and anon JWT. It is never cached for offline use. Worker v7 includes `push.js` and cleans only earlier RFID caches.

## Checks

`npm ci --ignore-scripts` then `npm test` runs the Node contract/UI tests and an actual PostgreSQL engine via PGlite, including RLS, transactional rollback, leases, expiry, ownership, source validation, and AES128GCM/VAPID verification. The suite includes cancellation between send batches and expired send authorizations. PGlite has one session and cannot certify concurrent enrollment/ingestion: the reviewed two-session probe is a required staged live check before PWA publication. `deno check functions/rfid-push/index.ts` validates the Edge entrypoint. In a restricted local environment, `deno check --node-modules-dir=manual functions/rfid-push/index.ts` can type-check against the exact npm-ci dependencies; that check does not exercise remote bundling. Native Android/iPhone Web Push and real service-worker lifecycle require a phone test.

Real-card test before relying on notifications: install the PWA on each Android and iPhone/iPad, open it from the Home Screen icon while online, press เปิดรับแจ้งเตือน and grant permission, press ทดสอบแจ้งเตือน, then close the PWA and lock the phone. Scan one enrolled card for a valid check-in. Verify one attendance effect and the correct name/date/scan time notification; tap it and compare the paired times in the app. Perform a valid checkout after the existing duplicate guard, then verify the checkout notification and original check-in time. Disable notifications on that phone and verify it stops receiving them. Test both installed Android and installed iPhone/iPad separately.
